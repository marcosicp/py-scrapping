# Deploy to Render (Docker runtime)

How to put LaListita on Render, and why the Dockerfile — not Render's native
Python runtime — owns the deployed environment. Status marks follow the same
legend as [`runbook.md`](runbook.md): ✅ VERIFIED (executed, output recorded),
📖 INFERRED (read from files or Render's docs, not executed here), and manual
dashboard steps are named as such explicitly.

## 1. Why Docker and not the native Python runtime

The deploy that started this failed before the app even booted:

```
ERROR: Ignored the following versions that require a different python version:
       4.19.0 Requires-Python >=3.11
ERROR: Could not find a version that satisfies the requirement pymongo==4.19.0
       (from versions: ..., 4.18.3)
```

Read that as an interpreter fingerprint, not a pin problem: `pymongo==4.19.0`
exists on PyPI and declares `Requires-Python >=3.11`; its predecessor
`4.18.3` declares `>=3.9`. pip only lists candidates compatible with the
running interpreter, so the ceiling `4.18.3` means **the build ran on Python
3.9 or 3.10** — not the 3.15 the repo declares everywhere (`.python-version`,
`Dockerfile:18`, CI).

Two independent causes, both specific to Render's native Python runtime:

- **Version precedence.** Render resolves the interpreter as
  `PYTHON_VERSION` env var > root `.python-version` > the service's
  creation-date default. Neither the repo's `.python-version` (3.15.2) nor the
  vestigial `runtime.txt` gets Render a 3.15: unreleased versions are only
  available through Docker, and **`runtime.txt` is not read at all** (it is a
  Heroku/Cloud Foundry artifact) — 📖 INFERRED from Render's docs; the error
  above is the observed signature.
- **No SPA.** `static/` is gitignored build output and
  `api/blueprints/frontend.py` answers **503** at `/` without it. A native
  Python build runs `pip install` only, so even a "green" native deploy serves
  a 503.

The Dockerfile solves both: its `node:24-alpine` frontend stage runs
`npm ci && npm run build` to produce `static/`, and the `python:3.15-slim`
runtime stage runs the interpreter the repo actually uses — the same image CI
and a developer can run locally.

## 2. MongoDB Atlas prerequisite

The API has no bundled database; `MONGODB_URI` must point at a reachable
MongoDB. For Render, Atlas is the straightforward choice (all manual steps in
the Atlas dashboard):

1. Create a free **M0 cluster**.
2. Create a **database user** (username + password under Database Access).
3. Allow ingress: either `0.0.0.0/0` (simplest; Render's egress IPs change) or
   Render's documented egress ranges under Network Access.
4. Take the `mongodb+srv://<user>:<password>@<cluster>/<db>` URI from Connect.

Fact worth recording: a fresh cluster means an **empty catalog** until a
scraper runs or the database is seeded some other way. `/` and `/scrape` work
with an empty database; `/supermercados` returns an empty grouped payload.

## 3. Two deploy paths

### (a) Blueprint — commit `render.yaml`

The repo root carries `render.yaml`, the deploy contract: a `type: web`,
`runtime: docker` service named `lalistita`, `dockerfilePath: ./Dockerfile`,
`healthCheckPath: /`, and the env vars from §4. `MONGODB_URI` is declared with
`sync: false`, so Render prompts for it in the dashboard on first deploy
instead of storing a secret in Git. `SECRET_KEY` is generated by Render
(`generateValue: true`).

Manual steps in the Render dashboard: **New → Blueprint**, pick the repo and
branch, paste the Atlas URI when prompted, apply. Committing a change to
`render.yaml` afterwards auto-triggers a Blueprint sync on the branch the
blueprint is bound to.

### (b) Existing service — switch the runtime manually

For a service that already exists (the failure above was created as a native
Python service): **Settings → Deploy → runtime: Docker**, keep the branch,
then add the env vars below by hand (Manual env-var entry in the dashboard —
there is no bulk import to verify in-repo).

**Warning: delete any stale `PYTHON_VERSION` env var on the service.** It is
meaningless under the Docker runtime and its precedence story (§1) is what
misled the original native-runtime attempt; leaving it set on a copy-pasted
service invites the same misdiagnosis.

## 4. Service environment variables

Same set, whichever path put the service in place:

| Variable | Value | Notes |
| --- | --- | --- |
| `SECRET_KEY` | generated (`generateValue: true`) | rotating the legacy `"secret!"` default is K-13 |
| `MONGODB_URI` | Atlas URI, `sync: false` | never in Git |
| `MONGODB_DB` | `lalistitadev` | collection `productos`; the URI's db segment is ignored |
| `CHROME_HEADLESS` | `1` | Render has no display; the scrapers must run `--headless=new` |
| `CHROMEDRIVER_PATH` | `/usr/bin/chromedriver` | Debian's package in the image |
| `CHROME_BINARY` | `/usr/bin/chromium` | Without it the driver guesses the browser binary heuristically (Selenium Manager probes candidate paths, chromedriver falls back to well-known names) and a guess that misses the image fails with `session not created`; this var pins `options.binary_location` through `Settings.chrome_binary` (`api/scrapers/browser.py`) |

The compute plan is deliberately left to the dashboard.

## 5. How to verify a deploy succeeded

Exact checks, in order — all 📖 INFERRED as an end-to-end set (each check's
behaviour is verified in-repo; the live Render URL was not reached from this
session):

```bash
# 1. The SPA route answers 200. 503 means the bundle is missing — the frontend
#    stage did not run, which under the Docker runtime should not happen.
curl -s -o /dev/null -w '%{http_code}' https://<service>.onrender.com/        # → 200

# 2. The control API reads the scraper registry (not the database), so it must
#    list the five slugs even with Mongo unreachable.
curl -s https://<service>.onrender.com/api/scrapers                           # → supermami, laanonima, disco, carrefour, changomas

# 3. The monitor page renders (registry-generated template).
curl -s -o /dev/null -w '%{http_code}' https://<service>.onrender.com/scrape  # → 200
```

In the dashboard's build log, the frontend stage must emit the npm build and
the runtime stage must copy the bundle into `/static`. If `/` is 200 but the
grid is empty, that is the empty-catalog state from §2, not a deploy failure.

## 6. Local pre-flight — the same image before pushing

```bash
docker build -t lalistita:local .
docker run --rm -p 8080:8080 -e PORT=8080 -e MONGODB_URI=mongodb+srv://... lalistita:local
```

New-runtime-layer facts, verified inside `python:3.15-slim` on Docker server
29.8.0: `apt-get install -y --no-install-recommends chromium chromium-driver
fonts-liberation ca-certificates` succeeds in one layer, and the binaries land
exactly where `render.yaml` points — `/usr/bin/chromium` and
`/usr/bin/chromedriver`. Note the *package* is `chromium-driver` but its
installed binary is `chromedriver` (not on PATH under the package name).

✅ VERIFIED end to end on 2026-11-06 (`docker build -t lalistita:verify .`):

| Check | Result |
| --- | --- |
| Frontend stage `npm ci && npm run build` | ✅ (requires the lockfile fix below) |
| `python -V` inside the image | `3.15.2` |
| `/app/static/index.html` present | ✅ 71 993 bytes |
| `/usr/bin/chromium`, `/usr/bin/chromedriver` present | ✅ |
| `GET /` / `GET /scrape` / `GET /api/scrapers` with `-e PORT=8080` and no reachable Mongo | `200` / `200` / `200` (five slugs) |
| `build_chrome(Settings.from_env())` inside the container with `CHROME_HEADLESS=1`, `CHROME_BINARY=/usr/bin/chromium`, `CHROMEDRIVER_PATH=/usr/bin/chromedriver` | ✅ launched Chromium `156.0.8078.79` headless, quit cleanly |
| Image size, default | **988 MB** |
| Image size, `--build-arg INSTALL_CHROMIUM=0` | **243 MB** |

Lockfile note (fixed in this branch): the first `docker build` died in the
*unchanged* frontend stage because `adminpro/package-lock.json` was out of sync
with `adminpro/package.json` — `npm ci` reported missing `@emnapi/core`,
`@emnapi/runtime`, `@emnapi/wasi-threads`. It was repaired by regenerating the
lockfile with the *same* npm the image uses (`npm install --package-lock-only
--ignore-scripts` inside `node:24-alpine`), which resolves hoisted
`picomatch`/`chokidar`/`readdirp` nesting and adds the three missing
`@emnapi` entries. Regenerate it the same way if `npm ci` ever desyncs again:
a macOS `npm install` produces a lockfile the Linux build then rejects.

Point the container at a throwaway database; every save REPLACES the scraper's
slice (`ProductRepository.replace_products`).

Lean image for a deploy that does not scrape:

```bash
docker build --build-arg INSTALL_CHROMIUM=0 -t lalistita:lean .
```

Without `MONGODB_URI` the app still boots (the Mongo client is always created)
— that is enough to smoke-test `/`, `/scrape` and `/api/scrapers`, which do
not touch the database.

## 7. Limits and risks — stated as facts

- **Free plan: 0.1 CPU / 512 MB.** Chromium does not fit there; scraping needs
  at least `1c-2g`. The free tier is fine for API-only deploys
  (`--build-arg INSTALL_CHROMIUM=0`).
- **The image is large because of the browser.** Chromium + its driver +
  fonts are a deliberate cost (988 MB against 243 MB lean), priced against the
  scrapers being the app's reason to exist.
- **Datacenter IPs are often blocked by the chains' WAFs.** A container with
  Chrome is necessary but **not sufficient** for a successful scrape from
  Render; real scraping against the supermarket APIs from a datacenter IP was
  not verified and is a manual test.
- **`static/` exists only because the frontend stage builds it.** Under the
  Docker runtime that is guaranteed; anything that reverts to a native
  runtime regresses to a 503 at `/`.

## 8. Troubleshooting

| Symptom | Cause → fix |
| --- | --- |
| `No matching distribution found for pymongo` (`Requires-Python >=3.11`, ceiling `4.18.3`) | The build ran on an old interpreter — a native Python runtime or a stale `PYTHON_VERSION` env var. Deploy the Dockerfile (§3) and delete `PYTHON_VERSION` (§3b). |
| `503` at `/` | `static/` missing — the frontend stage did not run. Confirm the build log shows `npm ci && npm run build` and the image is built from `Dockerfile` (§5). |
| `502` / health check (`healthCheckPath: /`) failing | The service is up but `/` errors, or the app died after bind. Check build log for the pip layer, then app logs; the port must match `PORT` — `ENV PORT=10000` is the Dockerfile default and Render injects `PORT` itself. |
| `chromedriver not found` / `session not created` on `POST /api/scrapers/<slug>/start` | Chromium or its driver did not land in the image (was it built with `INSTALL_CHROMIUM=0`?), or `CHROMEDRIVER_PATH` / `CHROME_BINARY` do not match the image's paths (`/usr/bin/chromedriver`, `/usr/bin/chromium` — §4). Rebuild with chromium and keep both vars. |
| Socket.IO transport stays on long-polling, no WebSocket upgrade | Expected, not a bug: neither `eventlet` nor `gevent` is installed, so `async_mode` resolves to `threading` (T-10 in [`known-issues.md`](known-issues.md)). Long-polling is the designed realtime path. |
